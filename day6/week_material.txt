1. git diff и git log решают разные задачи

Это главный косяк недели.
git diff

→ сравнивает содержимое.
git log A..B --oneline

→ сравнивает историю commit’ов.
git diff origin/feature feature

Поэтому:
git diff origin/feature feature

не отвечает на вопрос:
«Какие commit’ы есть в feature, но отсутствуют в origin/feature?»

Для этого:
git log origin/feature..feature --oneline

2. git log --oneline сам по себе не показывает расхождение веток

Твой вариант:
git log --oneline

может показать последние commit’ы текущей ветки.

Но если задача:
«Найди два commit’а, которых нет на remote»

нужно сравнивать две ссылки:
git log origin/feature..feature --oneline

Не просто смотреть последние два commit’а на глаз.

3. git diff --staged — не «показать staging»

Точнее:
git diff --staged

показывает:
разницу между staging и последним commit (HEAD).

То есть конкретно показывает, какие изменения уже подготовлены к commit.

Для working tree:
git diff
→ изменения между working tree и HEAD, которые ещё не staged.

Запомнить:
HEAD
 ↓
staging       ← git diff --staged
 ↓
working tree  ← git diff

4. reset --soft — не просто «откатить HEAD»

Твоя логика была правильной, но формулировку надо закрепить точнее.
git reset --soft HEAD~1

делает:
HEAD        → двигается назад
staging     → НЕ меняется
working tree→ НЕ меняется

Поэтому изменения отменённого commit остаются staged.

5. reset --hard затрагивает и staging, и working tree

git reset --hard HEAD~1

делает:
HEAD        → назад
staging     → состояние нового HEAD
working tree→ состояние нового HEAD

Поэтому незакоммиченные изменения могут быть уничтожены.

6. После rebase не надо автоматически переключаться на main

Это была твоя наиболее заметная операционная ошибка.

После:
git rebase main

если ты был на feature:
main    → E
feature → G'
HEAD    → feature

Поэтому если нужно отправить результат:
git push

А не:
git switch main
git push

Главная мысль:
main — название основной ветки проекта, а не команда «ветка, которую сейчас надо пушить».

7. Не путать локальный main и origin/main

После:
git fetch origin

ты получаешь актуальную информацию о remote:
origin/main
origin/feature

Но твои локальные:
main
feature 

сами от этого не перемещаются.

fetch:
обновляет информацию о remote, но не интегрирует её в твои локальные ветки.

8. fetch и pull — не обязательная пара

Ты несколько раз интуитивно строил:
git fetch
git pull

Но это не универсальная последовательность.

Например, ты находишься на feature и хочешь получить свежий main:
git fetch origin
git merge origin/main

pull здесь не нужен.

9. Rebase опубликованной истории

Вот это обязательно закрепляем.

Было:
origin/feature → ... → G

После rebase локально:
feature → ... → G'

G' — новый commit.

Поэтому:
git push

❌ обычный push не проходит.

Потому что remote уже содержит старую историю G, а локальная ветка её переписала.

В таком случае:
git push --force-with-lease

10. Почему в одном случае после rebase обычный push, а в другом force

Commit’ы были только локальными:
remote → E
local  → F' → G'

Обычный:
git push

✅
Commit’ы уже были опубликованы:
remote → F → G
local  → F' → G'

Обычный:
git push

❌
Нужен:
git push --force-with-lease

11. Не путать «другой человек работает локально» с изменениями на remote

Ты правильно заметил это в одной из задач.

Если другой человек просто что-то делает в своей локальной копии, его изменения никак не влияют на твой локальный репозиторий.

Проблема появляется, когда его изменения попадают в общий remote:
его local
   ↓
origin/feature
   ↓
твоя local

То есть для Git важен не сам факт:
«кто-то где-то работает», а состояние общей истории, которую ты видишь через remote.
